# java-rust-glowroot-agent 0.5.2

[English](0.5.2.md) | [Turkish](0.5.2.tr.md)

`0.5.2` completes the bounded Spring diagnostic path. Existing Java business logic, controllers,
services, validation, and Dubbo clients do not change. The Java edge forwards small metadata; the
isolated Rust exporter owns protobuf encoding, queues, error-stack materialization, collector I/O,
live JVM commands, reconnect, and resource release.

## What Users Get

| Area | Visible result |
| --- | --- |
| Endpoint dashboards | Exact route counts, Average, Percentile, Throughput, and Errors |
| Slow/error trace | HTTP method, response code, `http request`, controller timer/entry, and bounded thread counters |
| Spring Dubbo consumer | `dubbo consumer` timer, operation, call count, duration, and error count |
| Error | Original exception class/message/stack when available; otherwise `HTTP status 5xx` |
| Live JVM | Thread dump, OpenJ9 heap histogram/dump, Force GC, MBean tree, masked System properties |
| Environment | Host, CPU, physical memory, OS, process, Java/OpenJ9, masked JVM args, dump directory, agent version |

No SQL configuration is needed for a service that only calls Dubbo. The agent does not retain HTTP
bodies, query/header values, Dubbo arguments/results, or arbitrary operating-system environment
variables.

## Spring Boot Setup

```xml
<dependency>
  <groupId>com.reactor</groupId>
  <artifactId>java-rust-glowroot-spring-boot-starter</artifactId>
  <version>0.5.2</version>
</dependency>
```

Use the diagnostic profile on one incident pod:

```yaml
env:
  - name: REACTOR_GLOWROOT_ENABLED
    value: "true"
  - name: REACTOR_GLOWROOT_PROFILE
    value: "diagnostic"
  - name: REACTOR_GLOWROOT_SPRING_ENABLED
    value: "true"
  - name: REACTOR_GLOWROOT_COLLECTOR_ADDRESS
    value: "http://glowroot-central:8181"
  - name: REACTOR_GLOWROOT_AGENT_ID
    value: "nmc-store-common::$(POD_NAME)"
  - name: REACTOR_GLOWROOT_HTTP_SAMPLE_RATE
    value: "256"
  - name: REACTOR_GLOWROOT_TRACE_CAPACITY
    value: "8"
  - name: REACTOR_GLOWROOT_TRACE_SLOW_THRESHOLD_MS
    value: "500"
```

`sample-rate=256` affects optional normal-success trace detail only. It never samples endpoint
aggregates. Slow requests and failures are selected by their own rules. The trace queue remains
bounded at eight entries.

## Expected Startup Evidence

```text
Java-Rust Glowroot native telemetry active: abi=6, profile=diagnostic, application=nmc-store-common
Java-Rust Glowroot HTTP telemetry active: adapter=jetty-request-log, transaction-type=Web
Java-Rust Glowroot live diagnostics connected: agent-id=nmc-store-common::pod-name
```

The first line proves the JAR/SO ABI pair is active. The second proves HTTP completion is active.
The third proves Glowroot Central can send live JVM commands. Normal aggregate delivery and live
commands use separate HTTP/2 streams.

## Compatibility

| Component | Required line |
| --- | --- |
| Java | `21`; Semeru OpenJ9 is the primary JVM |
| Agent | `0.5.2` |
| Glowroot native ABI | `6` |
| Coordinated Rust-Java REST | `4.6.1` |
| Linux x64 | `glibc 2.17` or newer |
| Apache Dubbo adapter | Compiled against `3.3.0-beta.4`; uses the application's runtime |

Use the DLL/SO shipped by this exact release. Do not combine the `0.5.2` JAR with a native library
from `0.5.1` or an older Rust-Java REST package.

## Operational Boundary

Thread dumps are bounded. Heap histograms are capped at 4096 classes and a 1 MiB response. Heap
dumps can still create a large one-time JVM allocation and disk file. Run live diagnostic actions on
one pod during an incident, then return the profile to `micro` or the service's configured profile.

Application log weaving and arbitrary request payload capture are intentionally not part of this
release. Use redacted application logs or bounded domain metrics for searchable business values.
